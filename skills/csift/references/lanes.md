# Lanes: subagents (agents), which lane you are (whoami, @trap), teammates

Read this before listing a session's subagents or reading their status, before naming the lane you are running in or reading what your parent asked of you, before addressing or stopping a teammate, and before trusting an environment variable to say who you are.

## agents

`csift agents @<uuid>` lists a session's subagents as a parent-to-child tree (the nesting is rebuilt from spawn links; on disk every subagent transcript sits flat under `<session>/subagents/`). Three transcript shapes (`--shape`): `builtin-task` (`subagents/agent-<hex>.jsonl`, the Agent or Task tool), `workflow` (`subagents/workflows/wf_<id>/agent-<hex>.jsonl`), `teammate` (`subagents/agent-a<Name>-<hex>.jsonl`, marked by the sidecar meta's `taskKind:"in_process_teammate"`). `--agent-type T` (repeatable, exact) filters on what the agent is (`Explore`, `general-purpose`, `fork` for a `/fork` child), a separate axis from the shape. `--order-by trigger|start|completion` sets both the sort and the axis `--since`/`--until` filter on: `trigger` (default) is the parent's spawn call, `start` the child's first record, `completion` its last. `--agent <agent-id>` (bare or `@`) prints one node with its returned message and ignores the time, shape and type filters; with no target it searches every project, so add the session target when you know it. `--with-files` adds each node's changed files: a `files N changed` line and the list under each tree node, the `files_changed` array in JSON; `--agent` prints the count line and carries the JSON array without it, and the list only with it (measured: `csift agents @<uuid> --agent @<agent-id>` printed `files      6 changed` and no list, and with `--with-files` the six paths; the same tree without `--agent` printed no files line at all). `--returned-message` adds each node's returned message. `agents` has no span flag, and passing one exits 1 (measured: `csift agents @<uuid> --no-subagents`).

The text tree's count line reads `N subagent(s)  ·  kind=<shape or all>  ·  window-axis=<order>`, and it ends the output unless a teammate is in scope, when the three-line teammate note (Teammates, below) follows it after a blank line (measured: `csift agents @<uuid>` on a session with and one without a teammate). JSON is flat rows in tree pre-order: a `session` row `{session_id, runs, agents}` whose `agents` equals the number of agent rows that follow; a `run` row per workflow run `{session_id, run_id, task_id, workflow_name, status, agent_count, duration_ms, total_tokens, total_tool_calls, default_model, started_utc, started_local}`, where `status` is the run manifest's own word (an open set such as `completed`, `killed`, `failed`), null while a first run is still going (measured: 1 of 32 run rows of `csift agents @<uuid> --format json` during a live workflow), while a run resumed under its id keeps its killed predecessor's manifest, and so its word, until it ends (docs: `csift agents --help`); an `agent` row per node `{agent_id, path, shape, parent_session_id, parent_agent_id, spawn_tool_use_id, spawn_tool, workflow_id, agent_type, name, team_name, description, trigger_*, started_*, completed_*, last_activity_*, duration, depth, status, settled_by, pending_tool_use_id, pending_tool_name, pending_classification, pending_reason, pending_checker, pending_since_*, skipped_lines, fork_parent_last_uuid, fork_context_length}`, plus `routing_id` and `control_hint` on teammate rows only, `files_changed` and `returned_message`, `returned_message_source` when asked; a summary `{sessions, runs, agents}` (measured: `csift agents @<uuid> --format json`). Rebuild nesting from `parent_agent_id` and `depth`; `agent_id` is the node's own agent id, what other commands call `session_id`, and `parent_session_id` scopes its session.

A `/fork` child's node prints `forked-at <uuid> (context N)` (UNTESTED), and its `fork_parent_last_uuid` feeds `csift show @<parent_session_id> --uuid <it>`. `returned_message` is the newest message the child ever returned as the parent recorded it, which can be a terse sign-off plus the harness's appended continuation footer; on a lane that is not completed it predates the open call, and the text says `history — predates the still-open lane, NOT the outcome`. The child's own final words are among its last lines, `csift show @<agent-id> --line -30..`, the tail window references/search.md, show in depth, measures; a `--turn -1..` fetch of a one-turn lane stops at its first 200 records.

## Frozen lanes and status

A workflow lane takes its run's word first, by the rule `status` reads (references/live.md, What the evidence is made of), and such a lane has no completion instant; its row names the reason (JSON `settled_by`): `the workflow journal closes this agent (failed)`, `its workflow run ended (manifest status killed)`, or, for a lane that wrote more than a minute after its run's manifest ended, `its run's manifest (status killed) ended before this lane's newest record: the lane wrote after its run's end, most likely a run resumed under its id, so it is read from the lane's tail` (docs: `csift agents --help`; measured: `csift --claude-home FIXTURE agents @<uuid> --format json` on a synthetic run whose manifest reads `killed`: a lane 50 s past the manifest's end read `killed`, lanes 70 s and 5.5 min past read `completed` with that last text, and a journal `failed` line added for the second beat the manifest). `whoami --peers` and `wait --until stop` read such a lane by the same rule (UNTESTED). Any other lane is `completed` when its newest meaningful record is an assistant text ending its turn, and `running` or `unknown` otherwise; a tool result at the tail means the lane is mid-turn (docs: `csift agents --help`). A lane the person stopped mid-call, its tail a refused call's result and then `[Request interrupted by user for tool use]`, has no such text, so `agents` reads it `running` with no pending call and `csift status` reads it `unknown`; the age of its last record, `last_activity_*` here and the `tail` evidence row's age there, is the only sign it ended (measured: on one lane ending that way, `agents --agent` read `running` with `pending_tool_name` null and `status` read `unknown`, its tail 7,700,885 s old). `completed_*` and `duration` are set only when `status` is `completed`; `last_activity_*` is the tail instant on every lane.

`running` has no age bound: it says only that the lane's own transcript never settled it, so a lane of a session that ended weeks ago still reads `running` (measured: `csift --claude-home FIXTURE agents @<uuid> --format json` read `running`, `awaiting-execution` on a synthetic teammate whose last record was an unanswered call 239 days old). Whether anything runs now is `csift status @<uuid>`'s answer, and only while its evidence carries a `registry` row and `pid alive` (references/live.md).

When the newest record is an unanswered tool call the lane reads `running` with `pending_classification`: `escalation-blocked` (a Bash removal Claude Code holds for a person's approval even in bypass mode; the one waiting state a transcript can confirm) or `awaiting-execution` (slow, wedged or abandoned, which a transcript cannot tell apart). A lane pending for hours usually means its session ended; compare `pending_since_utc` with the current time yourself, and ask `csift status` about its session. `pending_reason` gives the harness's own reason text, or `removal target needs the filesystem state at the time` where the decision depends on the disk; `pending_checker` names which of Claude Code's two removal checkers the prediction ran and for which generation, from the record's `version` (`gen2 assumed` when there is none). A pending `PowerShell` call is always `awaiting-execution`, because csift does not parse PowerShell (UNTESTED). The classification fields are described in `csift agents --help` (docs).

## Which lane am I: whoami and @trap

`csift whoami` reads `$CLAUDE_CODE_SESSION_ID` (falling back to `$CODEX_COMPANION_SESSION_ID`). That variable names the TOP-LEVEL session in every lane: from a subagent it is the parent session's id, never the subagent's own, and csift says so on stderr, naming the variable that answered: ``csift: note: resolved via env ($CLAUDE_CODE_SESSION_ID), which names the TOP-LEVEL session in every lane - from a subagent this is the PARENT's id, not yours. Lane fields are null under env-only resolution; a first-try `whoami @trap:<marker>` hit proves your true lane.`` The parenthesis reads `$CODEX_COMPANION_SESSION_ID` when only that alias is set (measured: `env -u CLAUDE_CODE_SESSION_ID CODEX_COMPANION_SESSION_ID=<uuid> csift whoami`). The env form therefore reports `is_subagent`, `parent_session_id` and `depth` as null, a `lane unknown` line, and `parent   unknown from the environment alone (a top-level session has none; a subagent's parent is this session)`; a form that resolved the lane, such as `@trap:<marker>`, names the parent it resolved (measured: `csift whoami` and `csift whoami --format json` from a subagent, and `csift whoami @trap:<marker>` from the same subagent, which named the top-level session as `parent`). With neither variable set it exits 1 (`csift: error: cannot identify the calling session: CLAUDE_CODE_SESSION_ID is not set ...`) and prints on stdout the one way in from outside Claude Code; a value that is not a uuid also exits 1 (measured: `CLAUDE_CODE_SESSION_ID=not-a-uuid csift whoami`). It never guesses from file times.

To name your own lane, use `@trap:<marker>`: invent a marker and put it literally in the csift command; csift finds the transcript whose shell call carries it (a `Bash` call, or Windows' separate `PowerShell` tool). The marker is exactly three CamelCase words (each an uppercase letter and at least two lowercase) and four digits that neither repeat one digit nor rise or fall by a constant 1 or 2 (`1234`, `4321`, `1357`, `8642` are refused, `1470` passes), all picked by you and typed in this command. This file prints no example, because a copied marker collides with every other copy; the help page's own example is refused outright, as are a wrong word count, an all-caps word, three digits and a trivial digit run (measured: `csift whoami @trap:<marker>` exits 1 on each of those shapes, naming the rule it broke; references/errors.md quotes each message). Never build the marker in a script or from a variable, since the literal must appear in the recorded command. Two lanes that invent the same marker make it ambiguous; fold something only you know into it (a digit or two of your first tool call's id, the current second) and use it once. `csift whoami @trap:<marker>` prints your chain up to the root: identity rows for you (`depth` 0, `is_subagent` true) and for each ancestor to the top-level session, and a summary `identities` counting them (measured: `csift whoami @trap:<marker> --format json` from a subagent, first try: 2 identity rows).

Timing decides what a miss means. A subagent's transcript records each call as it starts, so from a subagent the first try resolves. The main conversation records a call only after the message completes, about 1 to 3.4 s after dispatch, and csift usually finishes first, so from the main thread a first try normally misses: use `@main` there, which needs no marker, or run the same command with the same marker again as a separate call (docs: `csift --help`, the @trap paragraph). A retry inside the same script runs in the same window and proves nothing; a fresh marker restarts the race. When `@trap` resolves to the main transcript, csift says so on stderr.

What your parent asked of you opens your transcript. In a built-in lane it is the first record, the spawn prompt, labelled `agent.communication.inbox` with the direction `<parent id> ⇨ self`: `csift show @<your agent id> --line 1`. A spawn prompt that merely quotes the word `fork-context-ref` is still that inbox record, because line 1's TYPE decides whether a lane is a fork child (a `type:"fork-context-ref"` record) and its text never does (measured: `csift search fork-context-ref @<uuid> -t agent.communication.inbox --format json` on a session whose briefs quote the word read 11 subagent lanes with line 1 labelled `agent.communication.inbox`, `from` the session and `to` `self`, and the same search under `-t user.message` read none at line 1). In a workflow lane L1 is that relay too, and when it is a short relay the task itself is L2, a `user.message` record opening `[Workflow harness — computed task]`, so read `csift show @<your agent id> --line 1..2` (measured on one session: 94 of its 250 workflow lanes carry the task at L2, one read of them under a relay of 630 characters, and the others carry it whole at L1, as did the built-in lane read). A subagent transcript can therefore hold `user.message` records that are not the person's: that computed task, and a follow-up message the parent sent later, so a spanning `-t user.message` over a session counts them as the person's (measured: `csift search '' @<uuid> -t user.message --count-by label` counted 230 records on that session and 136 with `--no-subagents`, the 94 extra all computed tasks; over one projects root 310 `user.message` records sat in subagent transcripts, 270 of them computed tasks at L2 and 32 later in a lane, 31 of those in built-in lanes, which a SendMessage to the lane's agent id resumes; that each is such a message is UNTESTED); scope the person's words with `@<uuid> --no-subagents`.

## whoami's lane sections and --peers

After the identity rows, `whoami` prints `self` (the lane's id, both teammate ids, kind, depth, state), `parent` (the lane above, whether it is alive, and the channel a reply would take) and `topology` (live child lanes, then a count of other live lanes). `csift whoami @<agent-id>` or `@<Name>@<Team>` answers these for another lane (rows `self`, `parent`, and a summary with `identities` 0); a session uuid is refused (measured: `csift whoami @<uuid>` exits 1). Lane kinds seen: `top-level session`, `unnamed subagent`, `teammate`, `workflow lane`. States: a top-level lane uses the registry's word (`busy`, `shell`, `idle`, `waiting`); a child lane is `in-flight` or `generating` when alive, and `self` can read `running`, `frozen` (an unanswered call at its tail, which is what your own lane shows while this command runs) or `completed` (measured: `csift whoami --peers --format json`, `csift whoami @trap:<marker>`).

`csift whoami --peers` lists every live lane as `id kind state` and nothing else, deliberately: a description or a role-like name is what one lane would use to claim authority over another, so the list says who is alive, never who to obey. JSON `peer` rows `{lane, lane_kind, session, state, last_activity_utc, last_activity_local}`, summary `{peers}`. `whoami --to` belongs to references/channel.md.

## Teammates: two ids, and how to stop one

A teammate has two ids. Its agent id `a<Name>-<16 hex>` (JSON `agent_id`; the hint below calls it the transcript id) is what the transcript file, hook payloads and every csift surface carry, and it is unique. The routing form `<Name>@<Team>` is a form TaskStop takes beside the bare name (docs: `csift agents --help`), and two same-named teammates in one team share it. csift accepts both as `@` targets (the routing form fails loud when two teammates share it, listing their agent ids) and prints both: `routing:` on the tree node, `routing_id` in JSON (measured: `csift agents @<uuid> --shape teammate --format json`).

Claude Code's two tools take different forms. The rules below are the ones `csift agents` prints, which csift read from the Claude Code 2.1.258 build (docs: that hint); the SendMessage and TaskStop schemas of a Claude Code 2.1.284 session name the same accepted forms (docs: those schemas, read 2026-09-30):

| tool | takes | refuses |
|---|---|---|
| SendMessage `to` | the bare name, or the agent id, which also resumes a teammate that is not running | any `to` carrying `@`, so never `<Name>@<Team>` |
| TaskStop `task_id` | the name or `<Name>@<Team>`, from Claude Code 2.1.198; earlier builds reject every form | the agent id, which is never a task id |

`csift agents` prints those rules as a footer under a tree holding a teammate (the first block below), and each teammate row's JSON `control_hint` states them again (the second) (measured: `csift agents @<uuid> --shape teammate`, and the same with `--format json`, identical on a synthetic session and on a live one):

```text
note: teammate rows are in-process Agent subagents — steer one with SendMessage addressed by its bare NAME (the `(@name)` shown, without the `@`), and terminate it with `message:{"type":"shutdown_request"}`.
      TaskStop also stops a teammate by its name or `name@team` from Claude Code 2.1.198 (earlier builds reject every form); the `aName-<hex>` id above is a transcript id, never a task id, and a teammate has no separate OS process (it shares the orchestrator PID — `pkill` won't help).
      the routing id Name@Team (the `routing:` field above) is a form TaskStop takes; SendMessage refuses any `to` carrying `@`, so that id is never a SendMessage `to`, which takes the bare name or a<Name>-<hex> (the id the hook payload and the transcript file carry, by which SendMessage also resumes a stopped teammate); the routing id can collide (two same-named teammates share it), the transcript id never does.
```

```text
in-process teammate: SendMessage to its bare `name` to steer (it refuses a `to` carrying `@`, so never `routing_id`), or to `agent_id`, which also resumes it when it is not running; message {type:"shutdown_request"} terminates; TaskStop by `name` or `routing_id` (Name@Team) also stops it from Claude Code 2.1.198 (never by the `agent_id` transcript id); shares the orchestrator PID (no separate process to kill). The two ids are minted apart: `routing_id` collides when two teammates share a name, while `agent_id` (a<Name>-<hex>), the id the hook payload and the transcript file carry, never does.
```

A teammate is an in-process subagent of its lead session, the session `csift agents` lists it under: it shares that session's process, so no process signal reaches it alone, and the stop call is the lead session's to make, through its own TaskStop or SendMessage (UNTESTED from any other lane). So first ask `csift status @<lead session uuid>` whether the lead is alive: without a `registry` row and `pid alive` in its evidence the lead has ended and nothing can reach the teammate, whatever `agents` calls it. Stopping one ends its work, and a SendMessage addressed to the agent id of one that already ended resumes it instead of stopping it (the SendMessage row above; docs: the `agents` hint above):

| action | irreversible: the call, its preview, the rule |
|---|---|
| stop a teammate | irreversible: TaskStop with `task_id` set to the name or `<Name>@<Team>`, or SendMessage with `to` set to the bare name and `message` `{"type":"shutdown_request","reason":"<why>"}` (which that schema says not to originate unless asked), ends the teammate's work, and once a TaskStop by the name or `<Name>@<Team>` has failed the SendMessage is the call left, since another TaskStop fails the same way; preview with `csift status @<uuid>`, whose evidence must carry a `registry` row and `pid alive` (the lead is alive; without both the lead has ended, nothing can reach the teammate and no call is made), and `csift agents @<uuid> --shape teammate`, which shows whether the name is unique and each teammate's status (`csift agents @<uuid> --agent @<agent id>` for one); when two teammates share the name, neither TaskStop form nor a SendMessage to the name can pick one, and the one call that does is SendMessage with `to` set to that teammate's agent id; a status of `completed`, `failed` or `killed` means it has already ended and no call is needed; the lead session calls only after the user's reply to that preview says go (the request that opened the task is not that reply) |

csift itself never stops, steers or messages a lane through Claude Code's tools; references/hooks.md has a hook that redirects a failed TaskStop.
